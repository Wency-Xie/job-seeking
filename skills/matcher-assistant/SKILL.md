# Matcher 助手 v0.1.0

## 原则

这是测试版，不是稳定版。只处理一个岗位，只读已确认网申档案，只写待审建议。不得修改 `job.json`、网申档案、投递意向、推进状态或任何人工编辑。

把模型判断限制在两件事：拆解 JD、把档案证据映射到要求。分数、门槛覆盖和最终建议必须由脚本复算。始终区分事实、推断和未知；没有来源原文或档案证据时不得补写。

## 单岗位工作流

1. 确认 JobSeekingOS 工作区与岗位 ID。运行：

   `python3 scripts/prepare_matcher_input.py --workspace <工作区> --job-id <岗位ID> --output <临时输入.json>`

   脚本只读取 `jobs/*/job.json` 与 `.workbench/personal-profile.json` 中的已确认档案，并保存 Skill、JD、档案版本和 SHA-256。临时输入含个人资料，放在受控临时目录，不提交 Git。

2. 按 [四层 JD 结构](references/jd-four-layer-schema.md) 拆解：硬门槛、最多 5 项核心能力、隐性期待、文化信号。每项都必须回链原文摘录；推断必须写依据和置信度，未知保持未知。

3. 只使用输入中的 `confirmedProfile`，按 [证据等级](references/evidence-rubric.md) 为每项核心能力和硬门槛映射证据。不得把“自述”“课程名”或相似关键词自动升级为直接证据。

4. 按 [建议文件格式](references/proposal-schema.md) 补全分析 JSON。不要自行计算最终分数或建议。

5. 运行：

   `python3 scripts/propose_matcher.py --workspace <工作区> --job-id <岗位ID> --input <分析.json>`

   脚本重新读取当前 JD 和已确认档案，检查版本与哈希，验证最多 5 项核心能力和原文回链，按确定性规则复算分数，写入该岗位 `assistants/matcher/proposal.json`。已有未审建议时拒绝覆盖。

6. 告知用户：结果是待审建议；Matcher 永远不自动修改“准备投递／未决定／暂不投”，也不把岗位标记为已投递。过期版本必须重新运行。

## 建议规则

- 档案完整度 `<60%`：`证据不足`，不以低分代替缺资料。
- 完整度 `>=60%` 且确认存在未满足的硬门槛：`暂不推荐`。
- 否则匹配度 `>=80%`：`可以投递`。
- 否则匹配度 `>=60%` 且 `<80%`：`补强后推荐`。
- 否则：`暂不推荐`。

核心能力证据分值固定为：直接证据 100、可迁移证据 70、自述或弱证据 30、无证据 0。各能力权重必须为正整数且总和为 100。详细规则见 [证据等级](references/evidence-rubric.md)。

## v0.1.0 边界

支持：单岗位、四层拆解、只读已确认档案、证据分级、确定性复算、待审 proposal、版本追踪、合成样例与只读影子验证。

暂不支持：全岗位批量队列、后台任务与进度弹窗、优先级视图重构、雷达图与完整筛选、福利自动调研、模型 API 自动调用、自动改变任何投递状态、稳定版发布。

## 验证

- 运行 `python3 -m unittest discover -s tests -p 'test_*.py'`。
- 真实岗位验证必须使用 `--shadow-output`，写到临时目录；不得写岗位 proposal，也不得显示完整个人档案。
- 至少核对：原文回链、事实/推断/未知、证据等级、版本哈希、脚本复算结果和零状态变更。
