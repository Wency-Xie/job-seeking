# 谈薪资助手

`v0.1.0` 是单岗位、待审核的测试版。它整理证据、拆解总包、识别信息缺口并生成候选话术；不代用户做决定，不执行对外沟通。

## JobSeekingOS 与人工确认

1. 读取 `jobs/*/job.json`，只处理“正在推进”视图中的岗位：候选岗位、`applicationTracker.advancing === true`、未结束且未暂停。读现有草稿、JD 和个人经历；预填样例不等于已核验事实。
2. 对市场与公司信息做当前检索，逐条记录链接、发布或检索日期、城市、岗位、届别或经验可比性。优先使用公司官网、校招公告、官方招聘页和可追溯的招聘样本；社交平台只能作低信心度线索。行业交流只能引用用户确实提供的交流。
3. 把固定月薪、发薪月数、试用期折扣、奖金、补贴、住宿、工作日、加班调休、五险一金、股权和签字费拆开，分别给出固定现金、保守总包和可能总包的口径；不把最高浮动值当成确定收入。
4. 形成四阶段候选内容：市场与岗位条件、个人价值与反问、报价依据与话术、Offer 比较与缓冲。先问预算和总包结构；证据不足时只生成待核实问题，不硬给报价。个人底线只供内部决策，不写进对 HR 的话术。
5. 按 [建议文件格式](references/proposal-schema.md) 写临时 JSON，运行 `scripts/propose_salary.py --workspace <JobSeekingOS目录> --job-id <岗位ID> --input <输入JSON>`。脚本只写该岗位 `assistants/salary/proposal.json`。不要直接修改 `draft.json`、`job.json` 或生成 Word。
6. 告知用户在谈薪助手预览并载入建议、逐项核对来源与数字。**只有用户点击“确认并保留 Codex 建议”，内容才进入正式岗位档案**；用户也可忽略本次建议。确认后可生成 Word 快照。

Codex 不得把待遇条目设为“已核对”，不得代用户勾选“我已核对”，不得以百分比宣布谈薪准备完成。不要自动给 HR 发消息、报价、接受或拒绝 Offer。

目标不是套用强硬话术，而是完成一条有证据的价值逻辑链：简历发出价值信号，自我介绍建立价值锚点，提问识别团队痛点，面试验证匹配，薪资兑现已验证的价值。

## 工作流

1. 先确认具体公司、岗位、城市、届别或经验年限、招聘阶段以及用户底线。缺少这些信息时标记待补，不猜测。
2. 投递前建立市场基准：分别记录招聘平台公开区间、真实行业交流、公司公开薪酬结构。每条信息保留来源、日期和可比性；来源不足时明确说明证据不足，不凑数。
3. 把月薪、发薪月数、绩效、年终、补贴、住宿、试用期折扣、股权和签约奖拆开，统一比较固定现金、保守总包和可能总包。不要把最高浮动值当成确定收入。
4. 面试中优先询问预算范围，使用合作姿态而非抢先报数字。需要主动报价时，选择市场基准、能力溢价或真实机会成本之一，并在数字前给出证据链。
5. 能力溢价只能引用简历、项目、面试反馈或可展示成果中已经验证的额外能力。没有证据的能力进入补强清单，不能包装为溢价。
6. 机会成本只能使用真实且可说明阶段的其他机会。不得虚构终面、Offer 或薪资范围。
7. 收到低于底线的报价时不当场承诺，记录差距并请求24小时缓冲；再比较岗位成长、总包结构、城市成本、住宿和风险。
8. 根据证据充分程度输出市场区间、个人底线、目标区间、策略、话术、需向 HR 追问的问题和证据缺口；不充分的字段保持空白。

详细调研字段、三种报价策略、SOP 与话术见 [谈薪作战手册](references/playbook.md)。

## 边界

- 不伪造工资流水、薪资证明、竞品 Offer、人脉反馈或公开数据。
- 不建议泄露前雇主、同事或候选人的保密薪酬信息。
- 市场数据有时效性；涉及当前行情时优先检索并注明日期。
- 最终数字必须由用户确认；不得自动向 HR 报价、接受或拒绝 Offer。
